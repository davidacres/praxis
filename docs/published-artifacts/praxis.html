ACP-native

One protocol layer, not a drawer of vendor SDKs

Each agent runs as an ACP process and Praxis speaks to all of them the same way. Orchestration, model discovery and session handling are written once, so adding an agent is a configuration change rather than a new integration.

Written once

Orchestration logic targets the protocol, not a vendor. Claude and Codex go through exactly the same code path.

Consistent model discovery

What each agent can do is discovered the same way for every agent, so routing decisions compare like with like.

No SDK tax

Vendor SDKs mostly add convenience: a bundled CLI and native types. ACP already covers the capabilities Praxis needs, so there's one less dependency to track per vendor.

Knowledge & memory

Memory that asks before it overrides

An MCP knowledge server gives every agent the same context at three scopes. When two scopes disagree, Praxis doesn't pick a winner quietly. It asks you, and it records your answer.

ORG

Organisation-wide. Standards, security policy and conventions that apply to every repository.

PROJECT

One codebase. Architecture, decisions and local exceptions to org policy.

LOCAL

One developer. Personal context and work in progress, kept on your machine.

Architecture decision records

Decisions numbered once, however many people write them

Project and org decisions are kept as Nygard-style ADRs. A shared MCP server hands out sequence numbers atomically, so two developers drafting on separate branches can't both claim the same ADR number.

ADRTitleStatus
0041Use ACP for all agent integrationsaccepted
0042Knowledge scopes: org, project, localaccepted
0043Reporting queries bypass repository layerproposed
0044[next number, reserved by the server]draft

No merge-time renumbering

The number is reserved when a draft is created, not when it merges. Duplicate IDs and the rebase that fixes them go away.

Agents read them too

Accepted ADRs feed the knowledge server, so review agents check changes against decisions your team has actually made.

Example records, for illustration.

Local-first

Keeps working when the network doesn't

A small local daemon sits between your tools and the central knowledge and ADR server. It isn't tied to any editor.

Cached reads

Knowledge and ADRs are served from a local cache, so agents keep their context offline.

Queued writes

Changes made offline are queued and forwarded to the central server when you reconnect.

VS Code extension

A thin client on the daemon for reviewing ADRs and resolving knowledge conflicts inside the editor.
