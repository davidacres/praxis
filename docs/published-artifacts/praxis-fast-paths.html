Praxis Fast Paths

Every guided screen in Praxis is optional. This is the short version: what to skip, what actually earns its place, and the keyboard route to all of it. If you have a repository already and want it under Praxis in under a minute, start at Bring your own repository.

Bring your own repository 01

Three steps, and Praxis reads the folder without writing to it. Detection looks for Git, README files, manifests, languages and frameworks, and fills in the project name and ticket prefix from what it finds.

Step 1Choose the folderNothing is created or modified during inspection.
Step 2Confirm what was detectedName, ticket prefix, and the project type — which decides the board's stages.
Step 3Review and addExactly what Praxis will record alongside the folder.

Reach it from the sidebar's New menu → Create from existing folder, or from the command palette with ⌘K → from folder. The brief, the board plan and the tool-access level all take their recommended defaults and stay editable from the project home afterwards.

If the folder is already a Praxis project, it says so. You are asked whether to use the existing project or create a second one against the same folder, rather than silently doing either.

Several repositories at once

The New menu also carries Import plans folders. Point it at a parent directory and it scans below, offering every Git repository that actually contains a plans structure — a repository with no discoverable plans is not offered rather than guessed at. Tick the rows you want, edit names and keys inline, and they are created in one batch. Each becomes a folder-backed project, so the markdown on disk stays the source of truth and the board reads it directly.

What to skip, what to keep 02

A new project is three steps unless you ask for more. Advanced setup — the checkbox on the first screen of either wizard — restores the full six, and also tells Praxis you do not need the first-run tour.

Safe to skip

  • Advanced setup. The brief, plan and tool-access screens all have defaults that are the same thing you would pick, and every one is editable from the project home.
  • The walkthrough. Offered once after a first project, never again. Ticking Advanced setup suppresses even that. Esc dismisses it and it counts as seen.
  • The Get Started strip on a project home. Dismissible per project, and it disappears on its own once the project has a session.
  • The splash. Full crawl on first run only; after that it is about a second. Click it to skip.

Worth the screen

  • The project type. It is not cosmetic — it picks the board's stages, the brief's questions, and five starter tickets. Changing it later means redoing the board.
  • Tool access, if the project is folder-backed. Full reads and edits files and runs commands; read-only does neither. Folderless projects are forced to project-board tools.
  • Where the workspace is stored, if you want the workspace file to travel with the repository rather than sit in the Praxis user folder.

Keyboard 03

The palette is the fastest route to anything with a name. It matches on a label prefix first, then a label substring, then anything else — so a couple of characters usually lands it.

KeyDoes
⌘K / Ctrl KOpen (or close) the command palette
⌘N / Ctrl NNew session composer
⌘R / Ctrl RReload the window
⌘I / Ctrl IFrom inside the terminal, open the terminal's AI input
↑ ↓ ↵Move and run inside the palette
EscClose the palette, a wizard, a dialog, or the walkthrough
TabEvery control paints a visible focus ring; the app is drivable without a mouse

Praxis remembers where you were 04

Reopening the last workspace at launch is on by default, and it restores the actual place — the project, the board, the open ticket, the session, even which git view you were in — not just the workspace.

Each workspace keeps its own place independently. Switching to another workspace and back returns you to where you left off in each, rather than dumping you on a landing page. Transient state deliberately does not survive: an unfinished form or a half-built session is not reopened for you.

Turn it off in Settings → Startup if you would rather choose a workspace each launch. With it off you land on the workspace list, and picking one still takes you to your last place inside it.

Workspaces that travel

A workspace can be saved to a .workspace.praxis file, and can be created with its storage in a folder you choose so the file sits with your repository instead of in the Praxis user folder. Credentials never go in it — those stay on the device.

Shaping the shell 05

The three panes — sidebar, main, and the right-hand context pane — are all resizable and hideable, and the sidebar has two modes.

ModeShows
ClassicThe full tree: projects with their boards, repository, workflows and documents, then the workspace-level features below
WorkA flatter view built around what is actually in flight — projects with their boards and current issues, for driving work rather than navigating structure

The right pane is context for whatever the centre is showing — a commit's detail on the Git Graph, a stage's settings in the workflow designer, a session's context in Sessions. It is not a fixed inspector, and it can be closed entirely.

The model, briefly 06

Worth two minutes because it explains why some things are where they are.

ThingIs
WorkspaceThe top-level context. Groups projects and owns connections. You always have one — skipping setup creates it rather than leaving you without.
ProjectA brief, a board, a workflow, and optionally a folder on disk. Its type fixes the board's stages.
ConnectionWhere real tickets come from: Jira Cloud, GitLab, GitHub, a folder of markdown plans, or the built-in demo data. A project can link boards from one.
SessionAn agent working a ticket. It plans, asks before using a tool, and reports what it changed. Provider, model and permissions are reviewable when it starts.
WorkflowA governed sequence of stages — agent tasks, checks, approvals — that runs against a project.

Backend support is uneven and worth knowing before you commit: Jira Cloud is the primary tracker with full board, issue, comment and transition support. Folder reads markdown plans from disk. GitLab covers connection and merge-request flows but its issue model does not match Jira's. GitHub gives a repository one board — columns synthesized from its own status: … labels — with the same three editable fields as GitLab plus comments and status moves. Demo is sample data, off by default.
